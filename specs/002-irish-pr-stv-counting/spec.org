* Implement reproducible Irish PR-STV counting
:PROPERTIES:
:CUSTOM_ID: summary
:END:

- Outcome :: A *Go counting engine* selects winning options and records an explainable, reproducible PR-STV count guided by the Irish system.
- Before :: The original definition established the counting rules and fixtures; initial Go-foundation implementation is now present. This refresh retains the *approved engine contract*.
- After :: A validated frozen ballot input and recorded decisions produce winners and the full count record.
- Changes :: Add the counting model, validation, quota, transfers, exclusions, last-vacancy handling, explicit decision requests, and independent fixtures. This refresh updates *architecture traceability and approval wording* without changing those rules or expected counts.
- Unchanged :: The engine has *no HTTP, database, email, participant identity, or scheduling ownership*. Irish PR-STV remains the guide; *legislative conformity is not required*.
- Edge cases :: Single winner, surplus rounding, last parcels, exhausted preferences, historical and unresolved ties, last vacancies, malformed decisions, replay, cancellation, and input bounds.
- Decisions :: Use *fixed Droop quota and whole-ballot transfers*, largest-remainder apportionment, recorded initial ballot order, and historical comparison followed by recorded lots. This specification defines the online-poll rules; legislation and Wikipedia provide guidance.
- Next step :: Review this architecture reconciliation and retain the recorded rule approval. Delivery depends on W001's Go module and current verification contract.

* Edge Cases
:PROPERTIES:
:CUSTOM_ID: edge-cases
:END:

- A winner may have a surplus in a one-place poll, but *no transfer is needed after that place is filled*. Covered by [[#ac-002-7][AC002.7 - Last vacancies terminate the count]].
- A ballot exhausting its preferences *remains accounted for* and does not lower the fixed quota. Covered by [[#ac-002-2][AC002.2 - Quota derives from ballots and places]] and [[#ac-002-6][AC002.6 - Exclusion transfers preserve preferences]].
- Equal totals do not automatically mean lots: *apply the application's specified historical comparisons first*. Covered by [[#ac-002-8][AC002.8 - Unresolved lots require explicit decisions]].
- A persisted decision may be syntactically valid but belong to another stage. The engine *rejects a mismatched request identity*. Covered by [[#ac-002-11][AC002.11 - Invalid decision records fail closed]].
- Empty input *returns an input error*, not invented winners. The poll-level zero-turnout outcome is specified in W003.

* Solution Design
:PROPERTIES:
:CUSTOM_ID: solution-design
:END:

** Architecture context

- Component :: =internal/count= with application-owned models and standard Go tests.
- Ownership :: W003 owns final ballot selection, storage, and execution. The engine owns *only the count transition and result*.
- Reuse :: No selected upload/writeback component supplies this rule implementation. Their application code must not become a dependency of the counting package.

** High-level design

*** Flow

1. Validate the rule version, options, place count, ballot IDs, and ranked preferences.
2. Create original parcels from the *explicit input ballot order* and calculate the fixed quota.
3. Apply the specified application count transitions. Preserve parcel provenance and intermediate totals.
4. On a required external selection, *return a decision request* rather than a final result.
5. Replay from the same input with the extended decision record; return the final count only when all required decisions have been validated and termination is established.

*** Interfaces and configuration

- API :: =Run(ctx, Input, []Decision) (Outcome, error)=.
- Input :: Schema version, rule-set identifier, immutable option IDs in declared order, winner count, and ballots containing opaque ID plus ordered option IDs. Ballot order is explicit and preserved.
- Outcome :: Exactly one of =Result= or =DecisionRequest=. A request is *not a counted result*. Invalid input, cancellation, and internal inconsistency return typed errors.
- Decision request :: Sequence number starting at 1, kind (=exclusion_lot=, =surplus_order_lot=, or =remainder_lot=), request fingerprint, eligible option IDs, and required selections (always 1). Candidate lots do not choose ballot order.
- Decision :: Matching request identity and selected eligible items. Reject duplicates, out-of-set selections, missing required selections, and trailing decisions after termination.
- Result :: Input fingerprint, schema/rule version, quota, winning IDs, ordered count records, and used decisions.
- Count record :: Totals, election/exclusion events, parcel transfers, non-transferable changes, and selection provenance. Do not serialize email addresses, participant IDs, or browser-facing text.
- Compatibility :: Version persisted structures explicitly. Unsupported versions fail; do not reinterpret an earlier count using a changed algorithm.

*** Online-poll counting rules

These rules define *irish-guided-stv-v1*. They are the complete application
procedure approved on 8 September 2026, using whole votes. Statutory administrative
rules and optional surplus-deferral thresholds are not part of this algorithm.

1. *Allocate and set quota.* Assign every ballot to its first preference. Each ballot has value 1. With N ballots and S places, set Q=floor(N/(S+1))+1 once. Keep this quota even as ballots exhaust.
2. *Recognize winners.* After the initial allocation or each complete transfer operation, elect every continuing option with tally at least Q. Elected options cannot receive later transfers. Record their election count and the incoming parcel that caused their election; original votes form that parcel for first-count winners.
3. *Check termination.* Stop immediately once S options are elected. Otherwise, if continuing options equal remaining places, elect all of them and stop, including options with zero votes. Winners form a set, not an ordinal ranking; output them in declared option order for stable presentation.
4. *Process pending surpluses before exclusions.* Among elected options with a positive unprocessed surplus, select the largest surplus. Break a surplus-size tie by the historical-high rule below, then request a surplus-order lot if needed. Examine all original ballots for a first-count winner, otherwise only the parcel received in the operation that elected it. Process each surplus once, even if no ballot can transfer.
5. *Apportion a surplus.* For the selected parcel, group transferable ballots by their next continuing preference, skipping elected/excluded options. Let U be the winner's tally minus Q, T the number of transferable ballots in the parcel, and p_i the count for destination i. If T=0, transfer nothing. If T<=U, transfer every transferable ballot. Otherwise assign floor(U*p_i/T) ballots to each destination, then allocate the remaining whole ballots in descending remainder order, where remainder=(U*p_i) mod T. Each destination receives at most one rounding increment. A remainder tie uses historical-high comparison, then a remainder lot for each unresolved boundary place.
6. *Choose and move ballots.* Within a destination group, choose the required number in the frozen input's ballot order. Move those whole ballots together. Unselected and non-transferable surplus ballots remain with the elected option, which may retain more than Q when T<U. Record destination counts, quotient/remainder calculations and selected ballot IDs. Each recipient's ballots from this operation form one incoming parcel. Return to winner recognition.
7. *Exclude when no pending surplus remains.* Sort continuing options by current tally only to identify the lowest set. Bulk-exclude the largest set of at least two lowest options whose combined tally is strictly less than the next option's tally, provided at least as many options as remaining places survive. A bulk boundary cannot split a tied tally. If no such set exists, exclude one lowest option, using historical-low comparison and then an exclusion lot if needed.
8. *Transfer exclusions as one operation.* Mark every option in the exclusion set excluded before locating next preferences. Move all their ballots to the next continuing preference. Ballots with none join the exhausted pile. Combine arrivals per destination into one parcel for this operation, preserving frozen input order. Return to winner recognition.

- Historical comparison :: Use completed count totals from earliest to latest, excluding the current count. At each count, keep only the tied options with the greatest total for historical-high, or the least total for historical-low. Continue until one remains or history is exhausted. A surplus comparison uses elected options' recorded historical totals; remainder/exclusion comparisons use the relevant continuing options. Never resolve a remaining tie by name, identifier or display order.
- Lot scope :: Request a lot only when its choice can change the next operation. If every member of a tied remainder group will receive an increment, give them all an increment without a lot. A supplied lot selects exactly one currently eligible ID. Recompute any following request after applying that choice.
- Ordered ballots :: The input order is an explicit count input, not a timestamp-based preference or candidate tie-break. W003 randomizes it once while constructing the snapshot and persists it. API tests provide a fixed order, making selected ballots and subsequent preferences reproducible.
- Progress :: Each operation elects/excludes an option or marks an elected option's surplus processed. There are at most 50 exclusion operations and 50 surplus operations; lot requests are bounded by the 50 options per operation. Cancellation is checked during validation, each operation, and each ballot scan.

*** Serialization and fingerprints

- Versions :: Input/output schema version is integer 1; rule identifier is =irish-guided-stv-v1=. IDs contain 1 through 64 ASCII letters, digits, underscores or hyphens. Reject other IDs, duplicate option/ballot IDs, overlong preference lists, and unsupported versions before counting.
- Input fingerprint :: SHA-256, lowercase hexadecimal, of compact UTF-8 JSON representing the array =[1,"irish-guided-stv-v1",optionIDs,S,ballots]=. Each ballot is =[ballotID,preferenceIDs]=. Arrays retain their declared order; no spaces or trailing newline are included. Restricted ASCII IDs make string encoding unambiguous. N derives from ballots and is not an independently mutable field.
- Request fingerprint :: Hash the same JSON encoding of =[inputFingerprint,sequence,kind,countIndex,eligibleIDs,1]=. Use declared option order for the eligible list; this orders the request presentation only and never selects the answer. Count 1 is the initial allocation; each completed surplus or exclusion operation increments the count index.
- Persistence :: Result and decision DTOs use explicit JSON field tags, slices for ordered records, integers for quantities and no map-dependent ordering. Store schema/rule version, fingerprints and decision provenance. W003 stores the input and returned structures without recomputing them under a different rule version.
- Invalid decisions :: Reject wrong sequence/kind/fingerprint, duplicate or ineligible selection, wrong selection count, and any unused trailing decision. Result is nil on error. A missing decision returns only DecisionRequest; a successful termination returns only Result.

*** Data and state

- Use *integer ballot counts* and exact quotient/remainder arithmetic; do not introduce fractional ballot weights.
- Maintain original/received parcel boundaries and ballot identities throughout transfer operations.
- Capture explicit decision inputs rather than relying on map iteration, identifier sorting, or hidden randomness.
- Per-count invariants account for every ballot among retained parcels, continuing parcels, and non-transferable parcels.
- The engine returns newly owned output and *does not mutate caller input*.

*** Failure behaviour

- Invalid inputs and unsupported rules fail before a count begins.
- A missing decision returns only the bounded request and diagnostic progress; it is not an exception or a provisional winner.
- Invalid decisions fail closed. A different valid decision record is a different count execution and remains distinguishable.
- Cancellation and failed conservation produce no authoritative result. W003 retains the frozen input for diagnosis and replay.

** Architecture impact

*** Security impact

- Threat boundary :: Untrusted ballot structure and persisted count inputs.
- Data and secrets :: Opaque ballot IDs and preferences are sufficient. No credentials or contact data enter the engine.
- Access :: No public route or database privilege is introduced.
- Mitigation :: Bounded collections, validated identifiers/decisions, exact arithmetic, cancellation, and explicit output versions.

*** Other relevant qualities

- Reliability :: Deterministic transitions and independently calculated fixtures; later retries reproduce the recorded path.
- Performance :: Bound the input and require progress through elections, exclusions, surplus processing, or a decision request. No unbounded retry loop lives in the engine.
- Operability :: Structured records permit diagnosis without rerunning against live mutable ballots.
- Accessibility :: No direct UI; W003 renders results and plain-language help.
- Portability :: Standard Go computation without native libraries or external commands.
- Maintainability :: Keep rule stages explicit and trace each unusual branch to its application rule and fixture. Any external counting dependency must implement those specified rules; legislative equivalence is not required.
