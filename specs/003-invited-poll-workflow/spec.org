* Context
:PROPERTIES:
:CUSTOM_ID: context
:END:

** Problem

An invited group needs a *simple voting experience* while the server preserves identity, final-ballot consistency, and a recoverable count.

** Outcome

A moderator can conduct the documented poll from preparation to outcome, and a participant invited through several addresses contributes *one revisable vote*.

** Scope

- In scope :: Configured moderator login; draft/edit/copy/open; grouped contacts; invitations; participant links/sessions; ranking and revision; pause/resume/close; automatic deadline processing; count persistence; results; optional email announcement; help; delivery status.

- Unchanged :: VISION's exact invitation and help copy, README's established voting rules, and ARCHITECTURE's Go/SQLite/Exodan component boundaries.

** Decisions

The following *first-release policies were approved with this specification* on 8 September 2026. README/VISION now reflect these decisions. The original proposal wording remains in Git and the dated audit history; it is not a current request to choose those policies again.

| Area | Approved policy |
|------+-----------------|
| Moderator authority | Each moderator administers only their own polls and copies only their own lists. An invited moderator may vote through a separate participant identity. |
| Visibility | The owner sees aggregate turnout, count detail, winners, and contact/delivery administration. No interface directly exposes another person's ballot or voting status. Small-poll results may permit inference; disclose this before voting, without a minimum-group-size restriction. A voter sees only their own current ballot. |
| Open-poll editing | Opening freezes question, options, winner count, deadline, participant grouping, and announcement setting. Corrections use a new draft copied from the old poll; no existing vote is silently reassigned. |
| Pause and deadline | Resume is available before the original deadline. The deadline closes both open and paused polls. Manual close is offered from paused state; closed polls never reopen. |
| Acceptance time | Take the server's UTC time after obtaining the write transaction. Accept only while open and strictly before the stored deadline. |
| Deadline entry | Enter a date/time with an explicit UTC offset; display UTC and the entered offset. Do not guess a timezone or ambiguous daylight-saving time. |
| Invalid ballots | Require at least one preference and consecutive unique ranks from 1. Reject gaps, ties, unknown options, or non-integer ranks without changing the last valid ballot. |
| Contact ambiguity | Trim and compare email addresses case-insensitively; de-duplicate within a participant, reject the same normalized address across participants in one poll. No inference joins separately entered people. |
| Announcement | Checkbox defaults off. If selected, send the short result email below to every invited address; no public result page is created. |
| Zero turnout | Close with a no-votes outcome and no winners; announce that outcome only if selected. Do not call W002 with empty input. |
| Returning access | Participant links are reusable for 24 hours; moderator links are one-use for 15 minutes. Sessions last 12 hours. Eligible users can request a fresh link. State/deadline checks always remain authoritative. |
| Retention | Keep polls, grouped contacts, final ballots, count records, and delivery outcomes for reuse and review. No automatic deletion of these poll records or anonymous-ballot promise is introduced. Expired technical sessions and rate-limit entries are cleaned up as specified below. |
| Input bounds | At most 1000 participants, 8 addresses each, 50 options, and 8 MiB per form body; text bounds are defined below. |
| Delivery timing | Declare a one-minute sweep interval. Announcement work is eligible when the result commits; normal processing attempts it in the same sweep if within the execution bound. |

These choices are *approved requirements*. Changes require explicit amendment; the product documents preserve their original questions and resolutions.

* Edge Cases

- Several invitations for one participant *never create several ballots*. Covered by [[#ac-003-3][AC003.3 - Several addresses share one participant]] and [[#ac-003-9][AC003.9 - Unlimited replacement of one vote]].

** Architecture context

** High-level design

*** Routes and interaction

| Boundary | Contract |
|----------+----------|
| /moderator/login | GET form, POST link request with generic confirmation. |
| /auth/verify | GET validates enough to render a continue form; POST validates CSRF and exchanges the token for a session, then redirects to a token-free URL. |
| /moderator/polls | GET owned list; POST creates a draft. Paginate in stable creation/ID order, 50 per page. |
| /moderator/polls/{id} | GET dashboard; POST updates draft fields only. |
| /moderator/polls/{id}/participants | GET/POST participant list, draft edits, and copy-from-owned-poll action. |
| /moderator/polls/{id}/open | POST validates and opens the draft atomically. |
| /moderator/polls/{id}/pause, /resume, /close | POST applies the permitted transition; close redirects to pending/result status. |
| /moderator/polls/{id}/results | GET owner-only result/count view or honest pending/failure status. |
| /polls/{id} | GET invitation-access information or the current participant's ballot/status. It reveals no electorate or results publicly. |
| /polls/{id}/access | POST requests a fresh link; known and unknown addresses receive the same response. |
| /polls/{id}/ballot | POST validates and replaces the participant's effective ballot. |
| /help/voting, /help/counting | GET public plain-English help from VISION, without poll data. |
| /logout | POST invalidates the current session and redirects. |

Successful mutations use POST/303 redirect/GET. Invalid fields return 422, stale
versions/invalid transitions 409, over-limit bodies 413, CSRF failures 403, and
unavailable storage 503. Unknown or unauthorized poll resources return the same
404 response, containing an ordinary link to the applicable access form.
GET /moderator/polls without a session redirects to /moderator/login; object
routes do not redirect differently according to whether the object exists.
Unknown routes return 404 and unsupported methods 405.

- Form decoding :: Accept application/x-www-form-urlencoded POST bodies, with normal charset parameters, bounded before parsing. Reject other media types with 415, unknown fields and duplicated scalar fields with 422. Explicit participant and rank collections may repeat only their declared indexed fields; reject duplicate option or participant identifiers. Escape all echoed input. RT003.17 includes media-type, multiplicity and unknown-field cases.
- Versions :: Draft updates, participant edits, open, pause and resume carry the poll version from the rendered form. Check it after obtaining the write transaction and increment it on mutation. A repeat of an already-applied open or close returns its current status without new work; other stale requests return 409. Ballots use their independent version, with version 0 representing no accepted ballot.

Use W001's defaults, host and decrypted-secrets loader for *both serve and

configuration. Values are loaded at process start. Moderator/key changes require
restarting serve; each scheduled invocation loads the current files.

*** Access and credentials

- Configuration history :: The former terse moderator/signing/SMTP key list is superseded by the complete schema and examples above.
- Construct all absolute poll, moderator login, participant invitation, and replacement links from the supplied =base_url= loaded through W001's configuration boundary. Neither =ADDR=, request Host, nor forwarded headers may select a link destination. URL/domain validation and deployment policy belong to Exodan; this application consumes the configuration without duplicating those checks.
- Sessions :: Use separate stv_moderator and stv_participant cookies; the latter holds one active poll scope per browser. Each value is 32 random bytes encoded base64url without padding; store only its SHA-256 hash, purpose, scope and 12-hour absolute expiry. Cookies are host-only, HttpOnly, SameSite=Lax, path=/, with Secure controlled only by http.secure_cookies. Logout revokes both current sessions. Session cookies are never accepted as grants.
- Grants :: Token format is base64url(payload) + dot + base64url(HMAC-SHA-256(payload)), without padding. Payload is versioned JSON containing v=1, key_id, purpose (moderator or participant), principal ID, poll/contact IDs when participant-scoped, issued_at/expires_at UTC Unix seconds and a 32-byte random nonce encoded base64url. Reject malformed, over-4096-byte, unknown-version, inactive-key and invalid-signature tokens before granting access. Compare MAC/hash in constant time and require the matching stored grant record to remain eligible. Moderator expiry is 15 minutes, participant expiry 24 hours; expiry equality is invalid.
- Grant recovery :: Persist claims and token hash so the sender can reconstruct the same signed grant without storing a raw bearer URL. Before an attempt, a grant with less than five minutes remaining or a different active key ID is atomically superseded by a fresh grant under the same logical delivery. The old grant is revoked; no second logical invitation is created. Normal separately requested participant links may coexist until their expiry.
- Key rotation :: Change auth.key_id with auth.signing_key and restart serve. Earlier-key grants cease to authenticate; pending mail gets fresh grants as above. Opaque existing sessions retain their own expiry and continue to check configured authority. Removing a moderator or changing their configured email invalidates grants/sessions tied to the previous configuration after restart; ownership records retain the stable ID.
- One-use moderator consumption and session creation occur in one transaction. Participant grants remain reusable within their lifetime. Every use checks the current configured moderator or poll participant.
- Grant/session lifetime is independent of voting eligibility. A valid session may display a closed poll's own-ballot status but cannot submit after closure.
- All authentication responses and ballot pages use no-store caching and a no-referrer policy. Logs exclude query tokens, cookies, SMTP credentials, ballot content, and unnecessary personal data.
- Link requests :: Accept replacements for configured moderators and contacts in open polls strictly before deadline. Paused/closed/nonexistent polls and unknown addresses receive the same 303 confirmation but queue nothing. Invitation work is held while paused and cancelled if still unsent at closing; announcements are independent of invitation cancellation.
- Throttling :: Permit one accepted link request per normalized identity/purpose/poll per minute and five in a rolling 15 minutes. Also permit at most 1000 link-request submissions globally in a rolling 15 minutes, counting known and unknown identities before queueing. Above either limit, return the same generic confirmation and queue nothing. Store hashed request keys/timestamps, purge entries older than 15 minutes, and cap stored rate records at 1000. No request-IP or forwarded-header interpretation is required; the earlier undefined source-address limit is withdrawn in favour of these application/mail limits.
- CSRF :: Every mutation requires a random 32-byte CSRF token bound to its session and verified against the stored hash. Public login/access forms use a distinct 15-minute pre-authentication session with host-only HttpOnly SameSite=Lax cookie and the configured Secure flag. Successful grant exchange rotates into the appropriate authenticated session. GET may establish this technical session but never consumes a grant or mutates poll/ballot state. No URL-supplied return destination is accepted; redirects use fixed application routes. Origin/Referer headers are neither authorization nor a separate filter: the session-bound token supplies CSRF protection, with SameSite as an additional browser control. No URL validation is added.
- Technical-session lifecycle :: Remove expired session records during authentication and each sweep; never remove poll/ballot records in this cleanup. Reuse a valid presented pre-authentication session. Permit at most 1000 live pre-authentication sessions, enforced transactionally; a form request requiring another session receives 503 when full. A successful exchange revokes its pre-authentication session and replaces the presented same-purpose authenticated session. This bounds abandoned-form state without interpreting proxy or client-IP headers.

*** Poll state and input

- States :: =draft=, =open=, =paused=, =closed=. Counting status is separate: =pending=, =awaiting_decision=, =succeeded=, or =failed=; =no_votes= is a completed poll outcome without an engine count.
- Transitions :: draft->open; open->paused; paused->open only before deadline; open/paused->closed at deadline; paused->closed manually. No other transition is accepted.
- Text :: Question 1 through 500 characters; option label 1 through 200; participant display name optional up to 100. Treat these as plain text and escape on output. A draft may be incomplete; opening requires valid fields, at least two options, one participant, one address per participant, and a future deadline.
- Options :: Unique stable IDs and distinct trimmed labels within the poll; winner count 1 through option count.
- Contacts :: Support bare mailbox addresses validated by the standard mail parser. Reject display-name forms and delimiter-containing quoted forms in this comma/colon input format; do not invent a permissive email regex.
- Draft participant edits :: Apply the submitted list atomically. Copying creates new participant/contact identifiers and excludes all ballots, grants, and delivery outcomes.
- Ballot form :: One labelled rank input per option, the current ballot version, CSRF token, and submit action. Unranked fields are blank. Validate the complete submitted ranking before replacing anything.

*** Storage and consistency

| Record | Required ownership and constraint |
|--------+-----------------------------------|
| Poll | Owner moderator ID, question, deadline instant and display offset, winners, announcement preference, state/version, created/closed timestamps. |
| Option | Poll ID, stable option ID, label, and display order; references cannot cross polls. |
| Poll participant | Poll ID and stable participant ID; identity is local to the poll. |
| Contact | Participant and poll association, delivery spelling and normalized email; normalized email is unique within a poll. |
| Grant and session | Purpose, principal/scope, hashed token, claims/key ID for grants, validity and consumption/revocation data; moderator records capture their configured normalized email for later authority comparison. Secret signing material stays outside SQLite. |
| Ballot | Unique poll/participant key, current version, ordered option IDs, and accepted timestamp. Keep only the effective revision in the first release. |
| Count snapshot | Unique closed-poll input, explicit ballot order, opaque count-only ballot IDs, options, place count, schema/rule version, and input fingerprint. |
| Count decisions/result | Unique sequence per snapshot and one authoritative result per snapshot; retain W002's structured record. |
| Work and delivery | Unique logical operation key, type, due time, bounded claim/token, attempts, status, and safe failure classification. Recipient scope and associated grant ID are explicit; superseding a grant preserves the delivery ID. |
| Link-request limits | Hashed identity/purpose/poll key and submission time; at most 1000 entries within a 15-minute window, with expired entries removed on request processing. No raw unknown email is retained. |

Each ballot mutation begins a write transaction, rechecks authority/state,
samples UTC time after obtaining the write boundary, checks version, and commits
the replacement. Closing uses that same serialization boundary to freeze the
input and insert count work. Database constraints remain the final protection
against two effective ballots, cross-poll references, and duplicate results.

The close transaction assigns fresh count-only ballot IDs, removes
participant/contact identifiers from the snapshot, and applies one uniform
Fisher-Yates shuffle using cryptographic randomness. It persists that exact order
with W002's schema=1 and rule=irish-guided-stv-v1 before any count runs. A failed
close, including shuffle failure, rolls back the entire close transaction and
leaves no snapshot or job. Manual close returns 503 for a safe retry; a scheduled
close records an operational failure and may retry on the next sweep. After the
deadline, the page says "Voting ended; results pending" even if the close has
not committed. A committed snapshot is never reshuffled.

W002's unresolved candidate lots are answered by uniform cryptographic selection
from its eligible list. Persist each request and answer, including its
fingerprint and sequence, under the current work claim before replaying the
engine. A unique snapshot/sequence constraint prevents competing answers; a retry
uses the already committed answer. Lot-selection RNG failure after a snapshot
exists produces a visible failed count, retaining that snapshot and earlier
decisions without a new answer or result. This is reproducibility, not ballot
anonymity.

- Result projection :: The engine's full record remains internal. Moderator HTML shows quota, aggregate turnout, per-option totals by count, elections/exclusions, aggregate transfers/exhaustion and option-level lot outcomes. It never returns snapshot JSON, ballot IDs/preferences, parcel membership or request fingerprints. Participant pages show only that participant's own current ballot and poll state.
- Privacy presentation :: Before voting, explain that one current ballot is stored per participant, moderators see aggregate results, and records are retained for review/list reuse. Include: "In a small poll, the results or turnout may allow someone to infer how a person voted or whether they took part." Do not promise anonymity: operators controlling storage can access the underlying associations. No individual-vote history or export route is introduced. Aggregate results without a group-size threshold were explicitly approved with this specification.

*** Due work and delivery

- Command :: =stv-poll process-due-work= uses the same configuration and database as serve. It reconciles due polls, advances counts, then dispatches due messages; it performs one bounded pass and exits.
- Bounds :: Maximum 60 seconds per invocation and 100 work items, including each close, count or delivery operation. Query in due-time/ID order, processing closing, counting and then delivery within the shared bound. A claim lasts 120 seconds; every mutation/acknowledgement checks its token, pending state and unexpired lease inside the transaction. Cancellation leaves unfinished work reclaimable; successful earlier operations remain committed.
- Command outcomes :: Help/version and invocation errors follow W001. No work or a healthy bounded batch exits 0; any attempted dependency/count/mail failure or execution-deadline cancellation exits 1 with a safe diagnostic. Existing terminal failures are not retried by each invocation and do not independently fail otherwise healthy sweeps. A full batch with remaining work exits 0; the next timer invocation resumes it. Emit one JSON stdout summary with version=1 and counts for closed, counted, no_votes, smtp_accepted, retrying, failed and cancelled; diagnostics go to stderr.
- Summary meanings :: Emit exactly those eight fields, all non-negative integers, for this invocation only. closed counts committed closes (including zero turnout); counted counts committed engine results; no_votes counts committed zero-turnout outcomes; smtp_accepted counts successful SMTP attempts; retrying counts attempts scheduled for retry; cancelled counts unsent deliveries cancelled by closing or expiry; failed counts failed attempted operations, including retryable failures, plus one for startup or execution-deadline failure. A retryable failure increments both failed and retrying. Startup failure emits failed=1 and all other counters zero. Invocation errors follow W001's exit 2/usage contract without a worker summary. Output contains no personal or secret values.
- Scheduler :: Declare a one-minute interval and this argument vector through Exodan's timer intent. The application creates no timer/cron/service definition.
- Result commit :: Store result, mark count work successful, and insert the logical announcement deliveries in one transaction. Never send before commit.
- SMTP :: Connect using the configured host/port and a 10-second overall attempt deadline. Require verified TLS through explicit implicit-TLS or required-STARTTLS mode; no opportunistic downgrade. Local plaintext SMTP is allowed only with an explicit development setting and a loopback destination.
- Retry :: Initial attempt plus at most five retries. After successive temporary failures, schedule 1, 2, 4, 8 and 16 minutes plus uniform jitter from 0 through 10% of that delay, persisted once with next_due. Permanent recipient rejection, authentication rejection and TLS policy/certificate failures become terminal immediately; temporary SMTP 4xx, connection failure and timeout/ambiguous acceptance are retryable. Persist attempt count and outcome. A process crash during an attempt consumes that started attempt; lease expiry schedules its bounded retry rather than resetting the counter. Tests inject jitter and inspect its persisted range/reuse.
- Attempt boundary :: Commit the incremented attempt counter and in-flight state before SMTP. Sending happens outside transactions. A final ambiguous/crashed sixth attempt becomes terminal failed after lease expiry; it cannot cause an unlimited retry loop. Before each attempt, recheck the grant and invitation eligibility under the claim. Closing atomically cancels unsent invitation/replacement jobs; an SMTP attempt already in progress may still arrive, but the closed-poll eligibility check prevents voting.
- Eligibility at send :: Invitation/replacement attempts require an open poll and time strictly before its deadline; paused work is held, and elapsed/closed work is cancelled without another attempt. An already-started SMTP operation may finish after pause or close. Moderator login mail instead checks the currently configured moderator; result announcements require a committed result and the recorded checkbox setting.
- Message construction :: Use text/template for the exact invitation body. Invitation subject is Vote: [thing]; moderator and participant replacement subjects are Sign in to STV Poll and Return to [thing]. Replacement bodies contain one short instruction and the recipient's link. Strip CR/LF from subject substitutions, encode non-ASCII headers with MIME encoded words, and use UTF-8 text/plain bodies. Each message has exactly one envelope/header recipient; no contact list or credential appears in logs.
- Visibility :: Show safe delivery states per contact to the owner, distinguishing queued, SMTP-accepted, retrying, and failed. Do not call SMTP acceptance "delivered to inbox".
- Logical uniqueness :: Initial invitations are unique per poll/contact; announcements per result/contact. A repeated HTTP action or worker does not create another logical operation. Physical SMTP duplicates remain possible after ambiguous acceptance.
- Failures :: A count error becomes visible and retains its snapshot/decisions; no automatic repeated count error loop is run. Infrastructure interruption reclaims unfinished work. Do not silently replace an existing successful result.

A zero-turnout announcement uses the same subject and states:

#+begin_example
No votes were received for [thing], so there is no winner.
#+end_example

Send each address its own message. The announcement does not include ballots,
contact lists, or a public result link. Invitations remain *exactly as in VISION*.

** Architecture impact

*** Security impact

- Threat boundary :: Public form/authentication endpoints, email bearer links, moderator ownership, participant identity, and persisted votes.
- Data and secrets :: The database retains personal contacts and ballot associations; *do not promise anonymity*. Consume Exodan's state-access boundary and disclose the approved retention/visibility policy in the UI; the application does not manage host ownership or permissions.
- Access :: Deny cross-owner/cross-poll access; derive participant identity from the scoped session, never a submitted email or arbitrary participant ID.
- Mitigation :: Atomic grant consumption, hashed sessions, explicit scope, CSRF, output escaping, bounded inputs, private pages, safe link origins, redacted logs, TLS mail, and dependency scanning.
- Approval :: Privacy, retention and announcement policies were included in the operator's original specification approval. This refresh preserves them; any later material change requires explicit sign-off.

*** Other relevant qualities

- Reliability :: Durable work, transactionally frozen inputs, persisted decisions, idempotent logical operations, and bounded recovery.
- Performance :: The stated limits bound first-release workload. Counts and network I/O never hold the database write transaction; no capacity claim substitutes for measured delivery evidence.
- Operability :: Owner-visible pending/failure states; structured CLI outcomes; serve and worker share the runtime contract. Use stopped-service SQLite backup/restore as the first documented consistency boundary, coordinated through Exodan rather than application-owned host scripts.
- Accessibility :: Native HTML, labelled inputs, field errors, keyboard focus, responsive CSS, and readily available help; human validation remains required.
- Portability :: Inherit W001's Darwin/Linux and listener contract.
- Maintainability :: Keep application services shared between HTTP and CLI, preserve reusable source provenance, and keep the counting algorithm in W002.

** Test architecture

Use standard Go =testing= and =httptest=, real temporary SQLite, injected time,
and a local capture transport/server for the owned SMTP boundary. Do not add
browser automation, source-text regression tests, live email, or metered service
calls to the persistent suite. UTs establish presentation and usability; OTs
establish the bounded local integration/packaging evidence.

- Web checks :: Inherit W001's *standalone Biome for CSS and tidy-html5 for rendered HTML*, alongside the separate Go lint/test commands. Extend rendered validation to moderator/access forms, ballots, validation/conflict responses, paused/closed/pending/result views and help, using synthetic state through the existing Go rendering/HTTP facilities. Do not validate unexpanded templates or add a browser stack. This workflow introduces no JavaScript/TypeScript, so oxlint remains conditional on a later approved change.
- Provisioning :: Reuse W001's pinned native tools and missing-tool/failure contract. No additional frontend runtime, package toolchain or production command dependency is introduced.
